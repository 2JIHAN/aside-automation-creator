# 파일 작성 규약

## 기본 구조

맞는 유형이 없으면 `assets/scenarios/basic/template/`에서 시작합니다. 기본형은 작은 파일 목록 보고서 업무를 예로 들어 검토, 알림, 자원 정리와 학습을 연결합니다. 다른 유형을 고르면 그 유형의 파일과 스텝을 사용합니다.

OS에 맞는 실행기와 설치 및 해제 스크립트를 한 세트로 선택합니다. 먼저 수동으로 검증하고 예약이 필요하면 주기와 등록 승인을 받은 뒤 설치합니다. 기본 설치 스크립트는 매시 지정 분 실행의 예시이며 다른 일정은 별도로 작성하고 검증합니다.

```text
<scenario>/
├── README.md
├── run.sh 또는 run.ps1
├── workflow/
│   ├── context.md
│   ├── mode.json
│   ├── flows/
│   │   ├── dev.json
│   │   └── operational.json
│   └── steps/
│       ├── dev-plan.md
│       ├── work.md
│       ├── review.md
│       ├── notify.md
│       ├── cleanup.md
│       └── learn.md
├── maintenance/
│   ├── install.sh 또는 install.ps1
│   ├── uninstall.sh 또는 uninstall.ps1
│   └── tests/
│       ├── 010-normal-flow.test.mjs
│       ├── 020-review-recovery.test.mjs
│       ├── 030-notify-idempotency.test.mjs
│       ├── 040-cleanup-learning.test.mjs
│       ├── 050-account-selection.test.mjs
│       ├── 060-installation.test.mjs
│       ├── 070-workflow-contract.test.mjs
│       └── test-helpers.mjs
└── runs/                         실행과 예약에서 생성
    ├── launchd.log               macOS 예약 로그
    └── <execution-id>/
        ├── run.json
        └── evidence/
            └── <turn>-<step>/
                └── <evidence-files>
```

기본형의 공통 기능이 모든 업무의 필수 권한을 뜻하지는 않습니다. 실제로 필요하고 허용된 범위에 맞춰 구성하고 단계나 상태를 바꾸면 테스트도 함께 맞춥니다.

## 개발과 운영 흐름

`workflow/mode.json`의 `mode`와 `flows`가 실행할 파일을 정합니다. 기본값은 `operational`이며, 기존 절차를 살펴보거나 수정하고 검증할 때 `dev`를 선택합니다. 개발 흐름은 점검 목적에 맞게 구성합니다. 제공하는 개발 예제는 `dev-plan` 한 턴으로 실행 결과 폴더의 `work-plan.md`만 작성합니다. 이 예제는 업무 지침을 계획 자료로 읽되 사이트 접속, 원본 처리, 외부 변경과 전송, 이월 메모 수정은 하지 않습니다. 개발 담당 에이전트가 계획 전문과 증거를 확인합니다. 운영의 기본 선택은 업무별 권한과 예약 등록 승인을 대신하지 않습니다.

업무별 운영 흐름은 `workflow/flows/operational.json`에 둡니다. 실행기는 선택한 흐름을 공통 엔진에 전달합니다. 엔진의 흐름 파일 생략 기본값은 기존 자동화 호환용이며 새 템플릿의 선택 경로가 아닙니다.

## 필수 배경지식 템플릿

`context.md`는 [이 템플릿](context-template.md)의 네 항목을 사용합니다. 시나리오에 필요한 배경만 간단히 작성하고, 실행할 행동과 순서, 판단 절차와 완료 조건은 해당 단계 문서에 둡니다. 서비스명이나 특정 업무의 목차를 모든 시나리오에 강제하지 않습니다.

## 작업 중 지식과 기록의 위치

시나리오를 함께 따라가며 새로 확인한 내용을 해당 문서에 바로 작성하거나 보완합니다. 전체 업무가 끝나거나 사용자가 별도로 정리를 요청할 때까지 기다리지 않습니다.

사용자의 조작과 설명에서 행동 순서, 판단에 쓰는 정보와 근거, 조건에 따라 달라지는 처리 방법을 파악합니다. 사용자가 규칙으로 기록하라고 지시하지 않아도 확인된 기준을 정리합니다. 이미 작성된 지침이 있으면 새로 확인된 내용에 맞게 스스로 보완합니다.

진행한 범위까지만 작성하고, 확인되지 않은 내용은 미확정으로 구분합니다. 문서를 미리 완성하려고 가상의 예외나 처리 절차를 늘리지 않습니다.

- 여러 단계에서 필요한 공통 배경과 개념은 context.md에 모읍니다.
- 해당 단계의 행동, 판단 절차와 완료 조건은 그 스텝 문서에 둡니다.
- 이번 실행에서만 확인한 관측값과 처리 결과는 실행 기록에 남깁니다. 일회성 사실을 지속적으로 사용할 지침으로 만들지 않습니다.

실제로 해보며 알게 된 내용은 그 내용이 필요한 단계의 본문에 반영합니다. 특정 단계에 속하지 않는 판단 기준만 스텝의 참고사항 절에 둡니다. 여러 단계에서 반복된다는 이유만으로 실행 절차를 context.md에 옮기지 않습니다.

문서 작성 때문에 업무 흐름을 자주 끊거나 단계마다 별도의 정리 승인을 요구하지 않습니다. 문서를 작성하기 위해 사용자가 정한 진행 범위를 넘기거나 업무를 앞서 수행하지 않습니다.

업무 결과와 이월 메모는 사람이 읽는 Markdown을 우선합니다. 프로그램이 직접 읽는 실행 설정과 `run.json`은 JSON으로 유지합니다. 파일 목록처럼 프로그램이 소비하는 결과는 JSON을 쓸 수 있으나 사람이 읽을 업무에 불필요한 필드 계약이나 저장 프로그램을 만들지 않습니다. 여러 수집 단계가 같은 결과 파일을 이어 쓸 때는 다른 단계의 기록을 보존하고 부분 완료와 전체 완료를 구분합니다.

브라우저 업무에서 `resources.md` 같은 자원 목록을 쓰면 이번 실행이 연 탭의 식별자와 소유 기록을 남깁니다. 정리는 해당 기록과 실제 탭을 대조하며 사용자와 다른 실행의 탭을 건드리지 않습니다. 파일명과 장부 자체는 업무에 필요할 때만 정합니다.

## 정식 지식과 학습 내용 연결

제작 중 확인한 정책과 명확한 사용자 피드백은 처음부터 담당 스텝이나 참조 자료에 직접 반영합니다. 별도 전역 학습 파일을 확정 지식의 저장소로 사용하지 않습니다. 기존 시나리오의 피드백을 반영할 때도 같은 기준을 적용합니다. 시나리오 수정 작업에서 받은 확정 피드백은 자동 실행의 `learn` 진입을 기다리지 않고 반영합니다. 자동 실행의 학습 진입 조건과 권한을 임의로 넓히지는 않습니다.

파일 구성을 정한 뒤 `context.md`에 문서별 역할을 작성합니다. 실제 생성한 문서의 시나리오 기준 경로와 담당하는 지식을 적고, 스텝이 사용할 참조 자료의 읽기 연결도 작성합니다. 템플릿에서 제외한 파일은 역할표에서도 지웁니다. 모든 도메인에 같은 참조 파일명을 강제하지 않습니다. 역할표는 수정 권한을 부여하지 않으며, 학습 허용 여부와 수정할 문서 범위는 별도로 확정합니다.

확정된 내용은 허용 범위 안에서 역할에 맞는 정식 문서에 직접 반영합니다. 정식 문서와 사용 경로를 확인하고 반영한 내용과 근거를 실행 증거에 남깁니다. 근거 사례는 실행 기록이나 증거에 보존합니다. 특정 대상의 사실을 전체 업무의 규칙으로 일반화하지 않습니다.

미검증 개선안과 후보 시험 기록은 해당 실행 증거에 남깁니다. 상황, 새로 알게 된 내용, 다음에 활용할 점과 적용 범위를 적습니다. 별도 학습 저장소는 필요할 때 역할, 수정 권한과 읽기 연결을 명시적으로 확정합니다. 기본 템플릿은 전역 학습 파일을 만들지 않습니다. 다른 자동화의 사례를 복사하거나 내용을 임의로 채우지 않습니다.

각 스텝은 같은 세션에서 공유한 필수 배경지식과 앞선 문맥을 전제로 새 행동, 판단과 완료 조건을 지시합니다. 배경을 반복하거나 자료 전체를 일괄 재독하게 하지 않습니다. 변할 수 있는 실제 상태의 재확인은 별개입니다.

제작 완료 전에 역할표의 경로가 실제 파일과 일치하고 해당 자료가 사용되는지 확인합니다. 확정 피드백의 정식 반영과 미확정 항목의 증거 보존도 임시 시나리오에서 확인합니다. 이 검사는 실제 외부 업무의 성공을 뜻하지 않습니다.

## 실행 폴더 전달

엔진은 첫 턴에 실행 결과 폴더의 실제 경로를 전달합니다. 같은 실행의 모든 턴이 이 폴더를 함께 사용합니다. 이번 턴 증거 폴더의 실제 경로는 매 턴 전달합니다. 업무 결과는 실행 결과 폴더에, 해당 턴의 관찰 증거는 이번 턴 증거 폴더에 둡니다. 업무 지침에서도 이 두 용어를 사용합니다.

## 파일 간 연결 규칙

- 공통 엔진을 사용합니다. 시나리오에 엔진 사본, Git 저장소나 `.gitignore`를 만들지 않습니다. 새 자동화는 `~/aside-automations/<slug>`에 만들고 기존 자동화의 경로는 유지합니다.
- `contextFile`과 `instructionFile`은 시나리오 기준 상대경로로 적고 실제 파일과 맞춥니다. `startStep`과 이동 규칙의 `step`은 파일명이 아니라 `steps`에 선언한 단계 ID를 가리킵니다.
- `initialState`에 `현재턴결과`와 필요한 상태를 선언합니다. `stateKey`와 `when`에서 쓰는 상태 키도 여기에 포함합니다. 단계 MD가 보고할 값과 선택한 흐름 파일의 기대값을 맞춥니다. 응답 값은 문자열이며 `현재턴결과`와 해당 `stateKey`에 반영됩니다.
- `when`은 값과 자료형이 같은지 비교합니다. 조건이 여러 개면 모두 일치해야 합니다. 결과마다 규칙 하나만 일치하도록 작성합니다. 빈 조건은 항상 일치하므로 다른 규칙과 겹치지 않게 합니다.
- 이동 규칙에는 `step` 또는 문자열 `finishWithStatus` 중 하나만 지정합니다. `$caller`는 `rememberCaller`로 기록한 출발 단계로만 복귀하며, 복귀를 중첩하지 않습니다. 같은 업무로 재확인하러 돌아가는 횟수는 두 번까지입니다.
- 여러 실행에서 함께 쓰는 상태 장부는 `runs/` 밖에 둡니다. 공통 엔진 테스트는 제작 저장소의 `tests/engine/`에, 업무별 테스트는 시나리오의 `maintenance/tests/`에 둡니다.
- 테스트 파일은 행동별로 나누고 각각 독립적인 임시 환경을 사용합니다. 파일 번호대로 실행될 것이라고 가정하지 않습니다. `test-helpers.mjs`에는 공통 준비 코드를 두고, 입력과 기대 결과는 각 테스트에서 바로 볼 수 있게 작성합니다.
